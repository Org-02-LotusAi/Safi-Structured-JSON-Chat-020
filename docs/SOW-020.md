SAFI  |  SERVICE STATEMENT OF WORK 020
Structured JSON SAFI Chat → NATS → OpenAI
Version 1.0  |  12 November 2026  |  ONE Developer · ONE Complete Product · SIX WORKING HOURS OR NOTHING
HOUR-6 RESULT / PAYMENT GATE: A non-developer user signs in to a working SAFI assistant-ui Chat, sends real multi-turn messages through server-validated SAFI JSON over actual NATS to the live OpenAI Responses API, and receives independently Ajv-validated Structured Outputs under either of two registered, version-pinned Schemas. SAFI alone determines acceptance.
1. Objective, completeness and independent ownership
Deliver ONE small but operational, reusable SAFI Chat-to-OpenAI Product. The user can hold a multi-turn text conversation, select one of two preapproved response contracts, see the resulting structured answer, and inspect its Schema ID, version and validation status. This Product uses the existing SAFI Chat standard; it is not an alternative Chat application or a prototype that skips NATS.
The Developer supplies and pays for an isolated pilot environment and the OpenAI API account. No dependency on SOW 016, Product 008, the unfinished SAFI hosting program, the proprietary Son-of-Root GUID Service, or another Fresher assignment. The final pilot is usable at one recorded, HTTPS-protected URL. No SAFI credentials, private data, or live Kernel privileges are needed.

4. Architecture and authority
Flow: assistant-ui (browser) → authenticated Fastify adapter → Ajv ingress check → Core NATS safi.chat.request.v1 → OpenAI Worker → approved Schema selection → live Responses API → independent Ajv result check → NATS reply → Fastify response → assistant-ui. A terminal, redacted receipt is published to JetStream safi.chat.audit.v1.
•  The backend authenticates the user, assigns accepted message IDs, and binds the browser session to a fixed pilot Sender GUID, OpenAI Service GUID, ordered Context (Thread GUID, Subject GUID), and authorized response Schema. Browser claims of GUID, Role, Context, NATS subject, model or raw Schema are ignored or rejected.
•  OpenAI is a Guest Service. It cannot alter the SAFI envelope, address a different participant, choose a Schema, grant permissions, run an operation, or classify its own reply as certified Final.
•  Only demo operational messages and bounded audit receipts are stored here. Neither JetStream records nor Ajv PASS constitute Kernel History, Logical Time, an approved Template, or Final proof certification. Chat History canonical ownership and Final representation remain outside this assignment.
•  Session scope is one independent pilot user at a time. Multi-user grants, full Root navigation, Moderator scheduling, protected Kernel admission and persistent transcript ownership require later SOWs.
5. Wire contract — registered SAFI JSON, not free-form strings
The project SHALL commit schemas/chat-request.schema.json, chat-result.schema.json and chat-error.schema.json. Request and return envelopes carry these normative fields; fields are validated before publish, before OpenAI invocation, and before sending back to the browser.
Field
Required semantics
protocol, version, kind
protocol="safi.chat", version="0.1.0"; kind="chat.request" | "chat.result" | "chat.error" as applicable.
message_id, conversation_id, in_reply_to
Opaque unique message/turn and conversation correlation. Reply references the exact request. Server checks route and correlation, never accepts cross-conversation substitution.
from_guid, to_guid
Fixed 16-byte (128-bit) test-only SAFI Object GUIDs represented consistently as lowercase 32-hex; Worker reverses directions for reply. Not production Kernel-issued IDs.
context
Ordered {thread_guid, subject_guid, path}; bound at protected backend. This is a Context reference, not a validated Grant.
schema_ref, schema_sha256
Registered {id,version} and digest; reply must match request. Browser may select approved ID only; cannot upload or mutate Schema.
sent_at_utc, body/status
UTC diagnostic timestamp (not Kernel clock); request body has text, reply body is typed JSON on status=ok. Refusal/incomplete/error are distinct typed error outcomes.
Use two immutable registered reply contracts: (A) safi.reply.summary/1.0.0: {reply:string, tone:neutral|friendly, followup_needed:boolean}; (B) safi.reply.tasks/1.0.0: {reply:string, tasks:[{task:string,priority:high|normal|low}], followup_needed:boolean}. All properties required, object additionalProperties=false throughout. An array may be empty. Schemas must use the strict OpenAI-supported JSON Schema subset and also compile with Ajv 2020.
6. Schema governance and OpenAI behavior
•  The allowlist is committed as schemas/registry.json. Each immutable entry names ID, version, file, SHA-256 and permitted UI choice. Schema selection is server checked; an unknown ID, digest mismatch, unsupported keyword, or unapproved version is rejected BEFORE any OpenAI call.
•  Use the exact approved strict-compatible Schema as OpenAI text.format and the separately compiled Ajv validator. Reject unsupported keywords during build/preflight; do not silently relax constraints or convert arbitrary user-supplied JSON Schema.
•  A response is successful only if OpenAI completed normally, returned parseable object JSON, the resulting object passes Ajv for the selected Schema, and the full SAFI reply envelope passes Ajv. Never coerce invalid JSON into valid JSON or display it as a certified success.
•  OpenAI refusals, incomplete/max-token outputs, timeouts, 429/rate errors and network failure receive typed failure results, visible to the user. Error text and logs omit API keys, tokens and private prompt contents.
•  Server constructs bounded multi-turn context from the current authenticated pilot session: last eight turns maximum, up to 4,000 input characters per user request, and no cross-session history. OpenAI store=false; do not rely on OpenAI-hosted conversation persistence.
7. Transport, cost controls and failure semantics
•  Core NATS request/reply has a 30-second bounded deadline. The Worker must be subscribed and the reply must match correlation, schema_ref and authorized addresses. Stop when adapter is absent; never return a canned OpenAI success.
•  JetStream stream SAFI_CHAT_AUDIT stores redacted request/outcome receipt (correlation, schema, result, model, usage, timestamp, error code) with bounded seven-day retention and configured maximum size. Persist receipts durably before reporting a completed outcome; explicitly report audit failure.
•  Configure a per-user request-rate ceiling (at most ten requests/minute), overall pilot API-call cap (default 40), max output tokens (512), payload-size cap and spend approval at H0. When limits are hit, reject before calling OpenAI.
•  Duplicate request_id in the live pilot MUST not launch a second API request; cache completed results for bounded idempotent retry. NATS and JetStream do NOT guarantee exactly-once OpenAI billing, especially after ambiguous failure: do not auto-retry unknown upstream completions. Log ambiguity and require an explicit new user turn.
•  No public NATS port. Credentials stay server side; TLS protects user access; secure short-lived pilot login cookie and server-side role/schema allowlist. No production OAuth/Auth system, Supabase, Windmill, or MCP built here.

11. End-user dogfood, recovery and SAFI acceptance
At least one independent, non-developer user uses the published site for 30 minutes before H6: ask a question and follow-up, select both approved Schemas, view the structured data and metadata, reload the site, and ask another question. Observer records the tester identity, exact URL, time window, browser/device, real API request IDs, screenshot of each Schema and any visible defect. Developer may explain the product but must not substitute a prepared video, hard-coded responses, or developer-only operation.
Operator proves controlled stop/restart of Worker and NATS, JetStream receipt recovery, user-readable outage, recovery to new live response, and remaining scope limits. A 30-minute newcomer onboarding rehearsal must succeed using README alone. The Developer supplies logs and evidence; SAFI independently judges the Product and payment.
12. Explicit exclusions and definition of DONE
OUT OF SCOPE: full Z Kernel, local Logical Time, Draft/Final certification, proprietary GUID generator, canonical durable Chat History, multi-user tenant/grant engine, Root context navigation, Meeting Manager/Moderator, Windmill, Supabase, MCP tools, external business operations, file uploads, speech, streaming token deltas, generalized Schema compiler, arbitrary OpenAI tools, enterprise production hardening and SAFI-owned hosting. No claims beyond the pilot.
DONE / PAYMENT GATE: A non-developer has actually used an HTTPS SAFI assistant-ui to exchange structured, schema-approved JSON with a real OpenAI model through real NATS; both registered Schemas pass, negative/security/recovery tests pass, and full replayable evidence plus source are committed by H6. Otherwise FAIL/BLOCKED; no “nearly done” or seventh hour. SAFI retains sole acceptance authority.
